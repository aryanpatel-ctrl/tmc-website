# Environments, promotion and rollback

Requirements: **R-4.7-3** (separate Dev, UAT, Production and DR environments), **R-4.7-4**
(controlled, auditable promotion with version control and rollback).

## The environments

| Environment | Where | Built by | `.env` from | Compose files | Project | Reached at |
|---|---|---|---|---|---|---|
| **Dev** | developer machine | `make setup` | `scripts/make-env.sh local` | `docker-compose.yml:compose.local.yml` | `tmc-website` | http://tmc.localhost (port 80, loopback) |
| **CI** | GitHub-hosted runner, new for every run | `.github/workflows/pipeline.yml` | `scripts/make-env.sh ci` | as Dev | `tmc-website` | inside the runner only |
| **UAT** | hetser (Tailscale only) | pipeline job *Deploy to UAT* on merge to `main` | `scripts/make-env.sh server` | `docker-compose.yml:compose.server.yml` | `tmc-website` | nginx-proxy-manager, http://tmc.100-79-142-44.sslip.io |
| **Production** | TMC's host (MeitY-empanelled, in India, in TMC's name) | `.github/workflows/release.yml` on a `v*` tag, after approval | `TMC_BASE_DOMAIN=<domain> scripts/make-env.sh prod` | `docker-compose.yml:compose.prod.yml` | `tmc-prod` | TMC's reverse proxy / load balancer (TLS) → `127.0.0.1:8080` |
| **DR** | second TMC host in India | restore from the off-host backup copy ([backup-and-dr.md](backup-and-dr.md#4-disaster-recovery-loss-of-the-production-host)) | `TMC_BASE_DOMAIN=<domain> scripts/make-env.sh dr` | as Production | `tmc-prod` | as Production after the DNS switch |
| DR drill | any Docker host, temporary | `scripts/dr/drill.sh`, `.github/workflows/dr-drill.yml` | generated by the drill | `docker-compose.yml:compose.dr.yml` | `tmc-dr` | nowhere (no published ports) |

Separation:

- **Own secrets per environment.** Each `.env` is generated on its own machine with random
  passwords and keys (`chmod 600`, never in Git, never in backups). Production secrets are also kept
  in TMC's secret store; DR uses production's `TMC_AUDIT_KEY` so the audit chain still verifies.
- **Own project, containers and volumes.** Production uses project `tmc-prod` and containers
  `tmc-prod-*`; the drill `tmc-dr` / `tmc-dr-*`. A UAT and a production stack on the same Docker host
  cannot share a volume, network or container name.
- **Unambiguous internal host names.** WordPress, WP-CLI, cron and backup reach the database and the
  cache as `tmc-mariadb` and `tmc-valkey`, network aliases that exist only on the stack's own
  `tmc_internal` network. On UAT the web container also joins the shared `homelab` network, where
  another project's container is called `redis`; with the plain service name the site used that
  server while WP-CLI used ours, so cache purges never reached visitors (found at the first UAT
  deploy of 30/09/2026). The gateway CI job enforces the aliases, and the smoke test proves after
  every deploy that a purge from WP-CLI reaches the site.
- **Deploy guard.** `scripts/deploy.sh` needs `TMC_DEPLOY_TARGET` (`uat` | `production`) to match
  `TMC_ENV` in the target directory's `.env` (`server` | `prod`); a UAT deploy can never land on
  production or the other way round.
- **Production mode.** `TMC_WP_ENVIRONMENT=production` sets `WP_ENVIRONMENT_TYPE`; on production the
  page cache leaves out its diagnostic reason header. Nothing else differs: the same images, code and
  provisioning run everywhere, so what was tested is what runs.
- **Proxy.** UAT routes through nginx-proxy-manager (`TMC_PROXY_ROUTE=npm`); production is routed by
  TMC's own reverse proxy (`TMC_PROXY_ROUTE=none`), which terminates TLS and sends
  `X-Forwarded-Proto` (honoured, see `docker-compose.yml`).

## Promotion: Dev → CI → UAT → Production

```
 Dev            CI (every push / PR)          UAT (merge to main)            Production (tag vX.Y.Z)
 ───            ────────────────────          ───────────────────            ───────────────────────
 make check ──► lint + six sites built    ──► pipeline.yml deploy job   ──► release.yml
                from scratch, all test        backup → sync → provision      1. gate: tag is on main AND that
                suites, smoke test            → proxy → smoke test →            commit passed the Pipeline on
                                              release recorded                 main (tested + deployed to UAT)
                                                                             2. verify: lint + full integration
                                              TMC UAT sign-off                  test again on a clean runner
                                              (R-4.14-6)                     3. deploy: waits for a required
                                                                                reviewer (GitHub environment
                                                                                "production"), then deploy.sh
                                                                                with TMC_DEPLOY_TARGET=production
```

1. Work on a branch; open a pull request. CI runs lint, builds all six sites from nothing, runs every
   test suite and the smoke test. Nothing touches a server.
2. Merge to `main`: the same checks run again and the commit is deployed to UAT
   (`scripts/deploy.sh`: backup → sync code → `scripts/setup.sh` → proxy route → smoke test → release
   recorded in `.release-history`).
3. TMC tests on UAT and signs off.
4. Tag **the commit UAT is running** and push the tag:
   ```bash
   cat ~/docker/tmc-website/.deployed          # on hetser: "<sha> <time> <actor> <run> uat"
   git tag -a v1.4.0 <sha> -m "Release 1.4.0: …" && git push origin v1.4.0
   ```
5. *Release to production* starts. The gate refuses a tag that is not on `main` or whose commit has
   no successful Pipeline run on `main`. After the verification job, a required reviewer approves in
   GitHub (Actions → the run → *Review deployments*). Approval, approver, tag and commit are recorded
   by GitHub and in `.release-history` on the production host (target and tag included).

The same deploy script, with the same backup-first and smoke-test-last steps, serves UAT and
production.

### One-time production setup (repository and host)

| Where | What |
|---|---|
| GitHub → Settings → Environments | environment `production`: *Required reviewers* (TMC release manager + vendor lead), *Deployment branches and tags*: tags `v*` only |
| GitHub → Settings → Rules | tag rule for `v*`: only maintainers may create; no deletion or update |
| Production host | Docker Engine + compose plugin; a deploy user; a self-hosted GitHub runner registered with the label `tmc-prod` (outbound HTTPS to GitHub only) |
| Production host | deployment directory (default `~/docker/tmc-website-prod`, or repository variable `TMC_PROD_DIR`): `git clone`, then `TMC_BASE_DOMAIN=<domain> scripts/make-env.sh prod`, store the generated secrets in TMC's secret store |
| Production host | off-host backup copy and its schedule ([backup-and-dr.md §2](backup-and-dr.md#2-off-host-copy-tmcs-backup-target-in-india)) |
| TMC's reverse proxy | forward the six host names (TLS) to `127.0.0.1:8080` on the production host with `X-Forwarded-Proto: https` |
| Monitoring | Uptime Kuma monitors ([monitoring.md](monitoring.md)) |

## Rollback

**Code** (a release misbehaves): Actions → *Release to production* → *Run workflow* → enter the
previous tag. The same gate and approval apply; `scripts/setup.sh` is idempotent and migrations only
move forward, so an older release runs on the current database as long as no migration changed data
in a way the old code cannot read (release notes say so when a release is not reversible).
UAT: Actions → *Pipeline* → *Run workflow* → an older commit or tag.

**Database** (a release damaged data): each deploy saved `backups/pre-deploy-<time>-<sha>.sql.gz` and a
full `pre-deploy` snapshot. Deploy the previous tag first, then restore:

```bash
scripts/dr/restore.sh --target ~/docker/tmc-website-prod --dump backups/pre-deploy-20260930-101500-abc1234.sql.gz --force
# or the full snapshot (database + uploads + configuration record):
docker compose exec backup tmc-backup list      # find the pre-deploy snapshot
scripts/dr/restore.sh --target ~/docker/tmc-website-prod --source-project tmc-prod --backup <name> --force
```

Content published between the deploy and the rollback is lost with a database rollback; the audit
log export (Network Admin → Audit log → CSV) of that window tells editors what to re-enter. Every
restore writes a safety dump of the database it replaces first.
